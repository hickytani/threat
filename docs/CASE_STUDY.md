# Portfolio Case Study: ThreatSync OS

**Project**: ThreatSync OS — Full-Stack Security Operations & Investigation Platform  
**Author**: Security / Backend Software Engineer  
**Codebase**: Next.js 14, NestJS, Prisma, BullMQ, Redis, PostgreSQL, TypeScript  

---

## 1. Problem Statement

Modern Security Operations Centers (SOCs) struggle with high event volumes, noisy alerts, and fragmented investigation tools. Security analysts often face three major challenges:
1. **Opaque Alerting**: Alerts generated by black-box heuristic or machine-learning models lack transparent evidence detailing *why* an alert fired.
2. **Cross-Tenant Data Leakage**: Multi-tenant security SaaS applications risk catastrophic IDOR vulnerabilities if tenant boundaries are enforced inconsistently across API handlers.
3. **Investigation Bottlenecks**: Telemetry events, asset risk ratings, and threat intelligence lookups exist in silos, forcing analysts to manually reconstruct attack timelines.

---

## 2. Project Goal

Build a production-grade, multi-tenant security operations platform capable of ingesting security telemetry, executing deterministic rule evaluations, correlating related alerts into evidence-backed incidents, generating transparent risk scores, and maintaining strict tenant isolation and auditable response workflows.

---

## 3. System Architecture

ThreatSync OS separates synchronous API operations from asynchronous queue processing:

- **Frontend**: Next.js 14 App Router console featuring dedicated investigation views for Alerts, Incidents, Assets, and IOCs.
- **Backend API**: NestJS modular application with centralized JWT authentication, tenant authorization guards, and typed DTO validation.
- **Asynchronous Pipeline**: BullMQ queue backed by Redis, processing event ingestion, deduplication, rule detection, and correlation asynchronously.
- **Persistence**: Prisma ORM with PostgreSQL, utilizing custom `TenantScopedRepository` wrappers to enforce database-level tenant isolation.

---

## 4. Key Engineering Challenges & Solutions

### A. Strict Tenant Data Isolation (IDOR Prevention)
- *Challenge*: Preventing unauthorized cross-tenant data access across multi-tenant organizations.
- *Solution*: Implemented a two-tier defense. First, NestJS `TenantGuard` extracts tenant context from verified JWT claims. Second, database access is routed through `TenantScopedRepository`, which injects `tenantId` into every Prisma query parameter (`where: { tenantId }`), guaranteeing that IDOR attempts return 404/403 exceptions.

### B. Deterministic Event Detection & Deduplication
- *Challenge*: Ingesting duplicate telemetry events and generating noisy, repetitive alerts.
- *Solution*: Developed a SHA-256 event fingerprinting mechanism based on `tenantId`, `source`, `eventAction`, `actorId`, `targetId`, and a 60-second timestamp window. Duplicate events increment a repeat counter instead of creating duplicate database records. Normalized events are evaluated against explicit, deterministic detection rules.

### C. Evidence-Backed Alert Correlation
- *Challenge*: Grouping disjointed alerts into actionable incidents without relying on unexplainable probabilistic models.
- *Solution*: Built `CorrelationService`, which links active alerts based on explicit relationships: shared asset IDs, user identities, IP/MAC network indicators, IOC hash matches, and a 1-hour temporal proximity window.

### D. Explainable Risk Scoring
- *Challenge*: Opaque numerical risk scores leave analysts unsure of why an asset is rated high-risk.
- *Solution*: Implemented an additive risk calculation engine in `AssetsService`. The score (0–100) aggregates base asset criticality, active alert severity weightings, and CVSS vulnerability scores. The API returns an explicit `contributors` array exposing exact point additions.

## 5. Security & Testing Baseline

- **Automated Testing**: 76 passing automated integration and unit tests across 7 test suites.
- **Test Coverage**: Covers JWT authentication, tenant guard access control, IDOR prevention, event deduplication, detection rule matching, queue worker retries, and incident state transitions.
- **Fail-Closed Access**: Unauthenticated or unauthorized requests fail closed by default.

---

## 6. Engineering Trade-offs

| Decision | Advantage | Trade-off |
| :--- | :--- | :--- |
| **Deterministic Detection over ML** | Zero false positives from model drift; 100% explainable alerts. | Requires explicit rule definitions for new attack techniques. |
| **BullMQ/Redis for Ingestion** | Sub-50ms HTTP ingestion latency; resilient background processing. | Introduces Redis state dependency in production. |
| **Local Intel Provider Fallback** | Deterministic offline testability; zero external API costs. | Requires manual seed update for offline indicator threat reputation. |

---

## 7. Verified System Limitations

- Events are ingested via REST HTTP APIs rather than native kernel-level eBPF/syslog agents.
- External threat intelligence enrichment relies on configured provider API keys; local deterministic tables are used by default.
- Active response actions (e.g. automated IP blocking) are not autonomously executed; incident resolution requires analyst authorization.

---

## 8. Summary Result

ThreatSync OS demonstrates a complete, serious security software engineering project. It proves deep understanding of multi-tenant architecture, backend security enforcement, asynchronous distributed job queues, transparent risk modeling, and full-stack technical execution.
